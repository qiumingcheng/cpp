# 跨机器研发工作区重建指南

本指南采用精简交付：外层 `qiumingcheng/cpp` 只保存 `AGENTS.md`、`CLAUDE.md -> AGENTS.md`、`.gitignore` 和本文件。三份实际文件加一个软链，不再单独上传 `integration/`、`deliverables/`、五个专题文档目录或历史实验包。版本和目录映射只维护在根 `AGENTS.md` §0.2，避免另存一份 lock 清单后发生漂移。

目标是重建可继续修改源码的研发工作区，保持 `cpp/各项目` 布局。产品代码、仓内文档和原生测试由已发布的五个产品仓库、八个特性分支取得；依赖、安装和新测试数据在目标机器按需准备。2026-11-08 发布本指南时未做新机器实测；2026-11-09 已在独立 openEuler 22.03 WSL 按八分支恢复源码、安装依赖并构建测试五个方向。当前源码 SHA、修复及精确验收范围见根 AGENTS.md §0.2。本指南仍需按目标环境配置，不意味着未发布的历史任务包、性能数据或72小时门已恢复。

## 1. 准备外层工作区

在目标环境获取 `qiumingcheng/cpp`，目录名使用 `cpp`。已有工作区直接保留，不用 clone 覆盖；以实际远端提交确认取得的资料版本。

在根 `AGENTS.md` 所在目录设置：

```bash
export CPP_WORKSPACE="$(pwd -P)"
```

先确认 Git、Python 3 可用，检查已有项目目录、dirty 文件与运行服务。源码和二进制版本分别记录；不要把旧实例默认端口、安装 hash 或性能数字当作新机器实况。不要复制原机器的 `.git` 文件或运行数据库来代替准备源码。

以下源码准备只用于用户允许的新环境；当前 WSL 目标仓不得因此被更新。提交和 push 继续遵守根 `AGENTS.md` 的云端约定。本节命令不执行 commit、push、构建或服务启停。

## 2. 按 AGENTS.md 的版本表恢复源码

下面的内嵌代码直接读取八行版本表，无需单独维护初始化脚本或 JSON 清单。它只创建不存在的目录；对已有目录仅检查固定 HEAD，不修改、不 fetch、不切分支。遇到差异立即停止并保留现场。

新建源码目录以 detached HEAD 固定到表中 SHA，防止远端分支后续变化导致恢复到另一版。对应特性分支名仍在版本表和 origin 中；后续开发、amend 与发布由云端按用户当次要求处理。

```bash
python3 - <<'PY'
import os
import re
import subprocess
from pathlib import Path

root = Path(os.environ['CPP_WORKSPACE']).resolve()
text = (root / 'AGENTS.md').read_text()
section = text.split('### 0.2 ', 1)[1].split('### 0.3 ', 1)[0]
rows = []
for line in section.splitlines():
    cells = [v.strip() for v in line.strip().strip('|').split('|')]
    if len(cells) != 5:
        continue
    match = re.search(r'https://github.com/(qiumingcheng/[A-Za-z0-9_-]+)', cells[1])
    sha = cells[3].strip('`')
    if match and re.fullmatch(r'[0-9a-f]{40}', sha):
        rows.append((match[1], cells[2].strip('`'), sha, cells[4].strip('`')))
if len(rows) != 8:
    raise SystemExit('版本表不是预期的八行，请先核对 AGENTS.md，未开始准备源码。')

def run(*args):
    subprocess.run(args, check=True)

def read(*args):
    return subprocess.check_output(args, text=True).strip()

for repo, branch, sha, relative in rows:
    dest = root / relative
    if not dest.resolve().is_relative_to(root) or dest.resolve() == root:
        raise SystemExit('项目路径越出工作区：' + relative)
    if dest.exists() or dest.is_symlink():
        top = Path(read('git', '-C', str(dest), 'rev-parse', '--show-toplevel')).resolve()
        head = read('git', '-C', str(dest), 'rev-parse', 'HEAD')
        if top != dest.resolve() or head != sha:
            raise SystemExit('已有目录版本或仓库不匹配，未修改：' + relative)
        print('保留已有工作树，未处理其 dirty 文件：', relative, head)
        continue
    dest.parent.mkdir(parents=True, exist_ok=True)
    run('git', 'clone', '--filter=blob:none', '--no-checkout', '--single-branch',
        '--branch', branch, 'https://github.com/' + repo + '.git', str(dest))
    exists = subprocess.run(['git', '-C', str(dest), 'cat-file', '-e', sha + '^{commit}'],
                            stdout=subprocess.DEVNULL, stderr=subprocess.DEVNULL)
    if exists.returncode:
        run('git', '-C', str(dest), 'fetch', '--no-tags', 'origin', sha)
    run('git', '-C', str(dest), 'checkout', '--detach', sha)
    if read('git', '-C', str(dest), 'rev-parse', 'HEAD') != sha:
        raise SystemExit('恢复后版本不匹配：' + relative)
    print('已恢复：', relative, sha)
PY
```

Python 需为 3.9 或以上。任一步失败时不自动删除已创建目录。固定 SHA 若已无法从远端获取，应查明发布记录并取得所需提交，不能静默换成默认分支或最新 HEAD。不要以本指南为由覆盖本机原有工作树。

## 4. 使用仓内入口重建开发环境

先按目标机器操作系统和 CPU 架构准备编译器、系统开发依赖、Python/Rust 工具链。版本要求优先读取该固定提交的 README、构建文件和工具链配置。`binarylibs` 等外部依赖需取得匹配发行版本及架构的材料，并记录来源、版本、校验值；本精简包不提供它们，依赖缺失时不能宣称构建环境已恢复。

### PG19＋ORCA＋Daft

跨仓脚本已在 pgorca 内，无需重建根级 `integration/`：

```bash
export PGD_WORKSPACE="$CPP_WORKSPACE"
export PGD_INTEGRATION_ROOT="$CPP_WORKSPACE/pg_orca/integration/pg19-pgorca-daft"
# 以下仅在获得相应构建/测试授权后执行。
bash "$PGD_INTEGRATION_ROOT/build_clean.sh"
```

Release Bridge 的传递依赖 daft-dashboard 需要 Node.js 22 以上及 npm 11.10.0 以上；构建前将其加入 PATH。仅有 Rust 工具链不足以完成该 Release 构建，不能以跳过资产生成代替安装依赖。

实例由同目录 `cluster.sh` 管理，阶段门和矩阵使用 `run_gate.sh`、`run_correctness_matrix.sh`、`run_fault_matrix.sh`、`run_packaging_matrix.sh` 等。先读取脚本支持的参数和实际依赖；不要盲跑全部门。

定向 ORCA 回归入口为 `pg_orca/test/test.sh --orca-tests <测试名>`，需要匹配的 `PG_CONFIG`、`PG_REGRESS_SQL` 和独立 `PG_ORCA_TEST_BUILD_DIR`。Daft Bridge 用例位于 `daft/src/daft-pg-bridge/tests/`，以该仓 Cargo workspace 和固定工具链为准。

已发布的 integration 有 16 个文件，无该目录 README。`quick_verification.sh`、`unit_verification.sh` 保留旧本机布局假定，不作为新机器首跑入口。`run_gate.sh P2` 仍依赖尚未交付的 `run_mixed_workload.sh`，不能据源码恢复便宣称 72 小时稳定性门可运行或已通过。

### openGauss 三个特性工作树

使用各自源码仓内 `build/script/build_opengauss.sh`，已支持 `-3rd <binarylibs>`、`-m debug|release`、`-mc on|off`。例如在选定特性仓中，按授权和实际依赖执行：

```bash
bash build/script/build_opengauss.sh -3rd "$CPP_WORKSPACE/binarylibs" -m debug -mc off
```

性能构建选择 release，随后核对实际配置和二进制。原生回归入口是 `src/test/regress/GNUmakefile` 及源码仓内 SQL/expected；根据选定特性使用对应测试目标。安装和初始化使用本次构建产物，为不同实例配置独立目录及端口；不覆盖旧数据库。

Python/psycopg2 测试使用系统 libpq；不要把 openGauss 的 LD_LIBRARY_PATH 传给 Python。原生 gsql、gs_ctl 等工具单独使用其安装目录的库路径，避免客户端 ABI 冲突。

本机 `deliverables` 的构建、重启和对标包装脚本未全部发布。这里使用可获得的仓内构建入口，不声称与旧包装脚本、旧安装二进制或性能配置完全等价，也无需在新机器凭猜测生成同名脚本。

### PG 原生图与 AGE

使用 `.worktrees/pg19-graph-core/postgres19/` 的原生 configure/Make 或 Meson 入口；安装到独立图环境，不复用协同计算 PG 的安装和数据库。构建配置按该固定提交的文档和本机依赖确定。
